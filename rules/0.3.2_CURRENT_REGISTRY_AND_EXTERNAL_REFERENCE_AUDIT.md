# OpenGLESScope 0.3.2 current registry and external comparison reference audit

## Finding

OpenGLESScope 0.3.1 correctly queried compressed texture, shader binary and program binary arrays from the active OpenGL ES implementation and already matched the public external comparison reference capability floor for the relevant core OpenGL ES capability families. Two current Khronos registry symbolic names were missing from the decoder: the HUAWEI shader/program binary formats registered/revised in January 2026.

The 0.3.1 README also contained stale release identity text (`0.2.3` headings and `versionCode 300` next to application version 0.3.1). This did not affect runtime behavior but violated release-metadata consistency.

## 0.3.2 corrections

- `0x9770` decodes as `GL_SHADER_BINARY_HUAWEI`.
- `0x9771` decodes as `GL_PROGRAM_BINARY_HUAWEI`.
- Both values remain reportable only when returned by the implementation's shader/program binary format arrays.
- Unknown values remain raw hexadecimal.
- README release/version metadata now matches Gradle.

## Capability-model result

- OpenGL ES identity remains queried from a real current context.
- Core 2.0/3.0/3.1/3.2 limits continue to satisfy the public external comparison reference comparison floor used by this project.
- Compressed texture formats are sourced only from `GL_NUM_COMPRESSED_TEXTURE_FORMATS` / `GL_COMPRESSED_TEXTURE_FORMATS`.
- Shader binary formats are sourced only from `GL_NUM_SHADER_BINARY_FORMATS` / `GL_SHADER_BINARY_FORMATS`.
- Program binary formats are queried only for OpenGL ES 3.0+ or exact `GL_OES_get_program_binary` evidence.
- UI, TXT, HTML and Database technical-report paths consume all three runtime arrays.
- Khronos specifications/registry remain authoritative over external comparison reference when newer registered tokens exist.
